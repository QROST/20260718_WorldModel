# Fashion Maze × Reactor

**English** | [简体中文](./README.zh-CN.md)

An HTML/React real-time world experience created for a SIGGRAPH hackathon. The
journey begins with a real rose-garden entrance image from the team dataset,
then enters a continuous video world generated by Reactor LingBot World 2.
Players explore an evolving fashion maze through world variations, WASD
movement, and camera controls.

**Authored and maintained by [QROST](https://qrost.github.io/).** Repository
files are covered by the SHA-256 manifest in
[`PROVENANCE.json`](./PROVENANCE.json). See
[`PROVENANCE.md`](./PROVENANCE.md) for authorship, team assets, and third-party
rights boundaries.

## Current experience

- Three 1376×768 rose-garden entrances come from the team dataset. The server
  randomly chooses one whenever the page opens, and the page and Reactor
  session remain locked to that image and its opening prompt.
- The same five white-and-cobalt couture performers are present from the first
  frame. Each performer retains their opening mark and every leg and foot's
  original position, height, angle, and contact state from the seed. A long
  runway hold, infrequent blinking, barely perceptible breathing, and minimal
  eye movement sustain a composed fashion-show tableau. They do not switch
  feet, shift weight, step in place, or move in response to the camera.
- The entrance retains only `THE INVITATION`, a small narrative, and one primary
  `Start live maze` action. It does not display an oversized entrance title.
- Route and Prompt definitions for Neon Canopy, Living Runway, and Golden
  Circuit remain as internal material, but the public experience no longer
  displays the three `Worlds Ahead` buttons.
- Scene 1 provides `ENTER THE BLACK DOOR`. The model first transforms an
  existing mid-distance arch or doorway in place into a richly ornamented frame
  integrated with the scene's materials. Beyond the threshold lies only
  uniform, featureless darkness. If no suitable opening exists, the frame may
  extend organically from an adjacent building, but it must never appear as a
  freestanding object. The door stabilizes for three complete chunks, after
  which the camera walks straight along the forward axis for eight confirmed
  real `forward` chunks, crossing the threshold and fully entering darkness in
  the final two. The web UI adds only a subtle 1.8-second push-in capped at
  1.1×, then a fixed black curtain fully covers the scene before reset.
- Every Start action draws a 32-bit run-order seed. The rose garden is always
  Scene 1; the other six authored scenes are fixed as Scenes 2–7 for that run
  using a no-repeat Fisher–Yates shuffle. A new order is drawn only after a
  disconnect and restart.
- Authored scenes include Cyberpunk Garden, two Asian Sculpture Garden scenes,
  two Afro-Futurism scenes, and Asian Fusion. Each scene still locks one random
  image from its own entrance material. `ensembleCount` remains application
  metadata and is never inserted into model Prompts.
- Each of the seven authored scenes uses a unique positional door question that
  is independent of the destination scene, so a randomized order cannot bind a
  question to the wrong next image. Every scene reuses the same
  environment-opening-first ornamental frame, pure darkness beyond the
  threshold, segmented straight walk, complete entry, and black-screen reset.
- After the seventh authored scene's black door completes, the Reactor session
  is released. The seven allowlisted seed images actually used in the run are
  then submitted to the server, where a `gpt-image-2` Images Edit request creates
  the runtime-only `SCENE 08 · The Grand Palais`. Story copy rotates while the
  image is generated.
- Scene 8 displays the generated image and `Attend the show`. Selecting it
  starts Reactor again from that image and restores the shared photo, WASD,
  camera, countdown, and session tools.
- Static preview is no longer a world selector; the invitation leads directly
  into the live maze.
- Prompts are organized as inspectable
  `base / anchor / camera / movement / destination / event / continuity`
  segments. Normal exploration uses one input-gated, observer-invariant camera
  contract so pressing or releasing WASD, arrow keys, or the mouse cannot create
  a one-chunk-delayed Prompt race. Photo and black-door actions select compact
  `locked / forward` layer versions.
- Reactor connects only after the user selects `ENTER LIVE MAZE`.
- On first connection, the reference image is uploaded only after observable
  `status === ready`. Generation is triggered through a once-only gate after
  both conditions are confirmed through either `conditions_ready` or the
  authoritative `state.has_image / has_prompt` path.
- The seed does not disappear when a black placeholder track first appears.
  After generation begins, it crossfades only when the track is live and
  unmuted, the video is playing, and two consecutive frames pass the non-black
  pixel check. The current hackathon mode does not automatically disconnect
  merely because a visible frame takes too long.
- Selecting a variation sends both a hot-swapped Prompt and a one-chunk forward
  instruction. After confirmation, the experience automatically returns to idle
  with the settled Prompt. The entrance seed does not invent a three-way fork.
- Every scene provides `TAKE PHOTO` and the `C` shortcut by default, using the
  shared `LOOK HERE → HOLD → SHUTTER` sequence. Scenes with people use confirmed
  `2 / 3 / 2` Prompt chunks: seed-visible performers first face the camera, then
  settle into position, then hold the shutter composition. Every beat is a
  compact, self-contained state description with no performer count, performer
  ID, outfit, or scene name. Empty scenes use three one-chunk environmental
  composition beats.
- The `SHUTTER` Prompt describes only the stable visible state of the completed
  pose; the browser performs the actual frame capture. After `chunk_complete`,
  the app first waits for 1.2 seconds of Reactor media time that has actually
  been presented, avoiding capture of an old frame that was emitted but not yet
  played. Browsers with frame callbacks use a media-time fence. The fallback
  also verifies presented-frame counts when playback-quality data is available,
  and otherwise uses `currentTime` as a best effort. Settling is only a quality
  optimization: after at most five seconds, a timeout or frame-callback error
  still saves the browser's currently drawable frame. The raw main-video frame
  is saved without HTML overlays, preferring WebP with a PNG fallback; download
  is attempted automatically and a receipt is shown. One release chunk lets
  current subjects relax their gaze, and controls unlock only after one real
  ambient Prompt chunk. Reactor Prompt and chunk confirmations have no
  application-level timeout.
- WASD controls only forward/backward and lateral movement of the observer
  camera; arrow keys control only camera view direction. No performer moves,
  turns, or tracks the camera in response to input. `MOUSE LOOK` uses native
  `setCameraPose()` with the video chunk clock.
- The `Session tools` drawer displays session, chunk, action, track, camera pose,
  timer gate, and final Prompt budget. Its collapsed `Debug event log` retains
  the latest 250 lifecycle events and can copy JSONL or be cleared manually.
  The implementation redacts common JWT, Bearer, API-key, blob URL, and local
  path formats, but logs should still be reviewed manually before sharing.
- When recording is available, an operator can capture, preview, and download
  the latest ten seconds as MP4.
- `keyup`, window blur, and page visibility loss all reset control state.
- `END SESSION` performs a non-recoverable disconnect. Input reset waits up to
  750 ms, and disconnect confirmation waits up to ten seconds. If the SDK does
  not confirm disconnection, the UI explicitly warns that the session may still
  be running and blocks the paid Scene 8 request.
- Every visible scene uses a prominent `30 → 0` remaining-time countdown. It
  changes to a warning color for the final ten seconds and pulses faster for the
  final five. When time expires in any of the seven authored scenes, the door
  question opens after the current photo, route, or pause action finishes and
  controls recover. The seventh question enters the generated finale. Scene 8
  has no following scene, so it remains live at `0` until the user selects
  `END SESSION`.
- The current unbounded-wait hackathon policy allows connection readiness,
  entrance arming, start, route, photo, door-question, and cross-scene generation
  to wait indefinitely without an application watchdog disconnect. A visible
  `END SESSION` action remains available while the black curtain waits for the
  next scene. Explicit SDK or API command errors still end sessions that cannot
  be recovered reliably.
- The ensemble's “pause” is a Prompt-held pose; live generation and billing
  continue. The SDK `pause()` action is explicitly labeled
  `FREEZE STREAM · STILL BILLED`.
- The UI clearly distinguishes `STATIC PREVIEW`, `LIVE`, and
  `PAUSED · STILL BILLED`.

## Installation and running

```bash
pnpm install
pnpm dev
```

Open `http://localhost:3000`. Static preview does not request a JWT or create a
Reactor session.

### Demo scripts

The repository root provides five entry points with no parameters to remember:

```bash
./setup-demo.sh       # Install the dependency set pinned by the lockfile
./build-demo.sh       # Sync dependencies, typecheck, verify offline, and build
./check-demo-keys.sh  # Check credential presence without printing key values
./start-demo.sh       # Start the loopback-only production demo
./start-dev.sh        # Start the loopback-only development server
```

You can run `./start-demo.sh` directly from a clean clone; it prepares missing
dependencies or a missing production build automatically. For a formal demo,
run `./setup-demo.sh` and `./build-demo.sh` in advance, then run only
`./start-demo.sh` on site. First-time installation requires package-registry
access. Builds and launches use the lockfile-pinned dependency set. These scripts
never print, create, or copy API keys, and installation and build steps do not
connect to Reactor or OpenAI. If a live Reactor session has started, select
`End Session` in the page before stopping the local server.

### Obtaining and storing API keys

Reactor and OpenAI are separate services. Assuming the corresponding accounts
have model access and credits, the available experience is:

| Reactor key | OpenAI key | Available experience |
| --- | --- | --- |
| Missing | Either | Static preview only; no Reactor session is created |
| Configured | Missing | Live maze for Scenes 1–7; Scene 8 is unavailable |
| Configured | Configured | Full Scenes 1–8 experience |

1. **Reactor:** Open [Reactor API Keys](https://www.reactor.inc/account/api-keys),
   sign in or register, and create a key. Reactor documentation states that keys
   begin with `rk_`. Also confirm that the account has LingBot World 2 access and
   credits. See [Reactor Authentication](https://docs.reactor.inc/authentication)
   and the [LingBot World 2 API](https://www.reactor.inc/models/lingbot-world-2/api).
2. **OpenAI:** Create a key under
   [OpenAI Platform API Keys](https://platform.openai.com/settings/organization/api-keys)
   and confirm API billing in the
   [Billing Overview](https://platform.openai.com/account/billing/overview).
   Scene 8 uses `gpt-image-2`; the official
   [image generation guide](https://developers.openai.com/api/docs/guides/image-generation)
   notes that GPT Image models may also require verification in
   [Organization settings](https://platform.openai.com/settings/organization/general).
   OpenAI API billing is separate from ChatGPT subscriptions; ChatGPT Plus or
   Pro alone does not provide API credits. See
   [API key safety best practices](https://developers.openai.com/api/docs/guides/production-best-practices#api-keys).

After obtaining the keys, choose one storage method.

**A. Recommended: use `.env.local` in the repository root**

If `.env.local` does not exist, initialize it and restrict its permissions:

```bash
cp .env.example .env.local
chmod 600 .env.local
```

Then edit `.env.local`:

```bash
REACTOR_API_KEY=<paste-your-reactor-key>
OPENAI_API_KEY=<paste-your-openai-key>
```

**B. Local hackathon fallback: use key files in the repository root**

- `./reactor.key`: one raw Reactor key and nothing else.
- `./openai.key`: one raw OpenAI key and nothing else.

```bash
chmod 600 reactor.key
chmod 600 openai.key
```

Restart `./start-demo.sh` or `./start-dev.sh` after saving credentials; Next.js
reads them when the server starts. You can run `./check-demo-keys.sh` first. It
reports only whether a credential was detected and never prints its value.

`.env.local`, `.env.*`, and all `*.key` files are ignored by Git. Never put real
keys in `.env.example`, a `NEXT_PUBLIC_*` variable, source code, README files,
screenshots, or logs. Manual ZIP/Finder copies do not honor `.gitignore`, so
exclude these files explicitly before delivery. The Reactor key never enters the
browser; the browser receives only a short-lived JWT from
`POST /api/reactor/token`. The OpenAI key is read only by the server-side Scene 8
route. Production deployments should use the hosting platform's secret manager,
not key files.

## Content package and narrative

The current content is incorporated read-only from the original Fashion Maze
authoring repository. Portable source specs and the 14-scene registry live in
[`content/authoring/`](./content/authoring/). Runtime entrance and performer
images live in [`public/dataset/`](./public/dataset/), and mapping decisions are
documented in [`content/README.md`](./content/README.md). Runtime content is
centralized in [`lib/fashion-maze.ts`](./lib/fashion-maze.ts). Each maze has the
following structure:

```ts
interface FashionMaze {
  id: string;
  entrySelectable?: boolean;
  title: string;
  seedImage: string;
  openingPrompt: string;
  entranceVariants: Array<{
    id: string;
    label: string;
    seedImage: string;
    seed: number;
    openingPrompt: string;
    ensembleCount?: number | "all"; // app metadata; never inserted into Prompt text
  }>;
  seed: number;
  entrance: NarrativeBeat;
  basePrompt: string;
  defaultDestinationPrompt: string;
  promptLayers: {
    movement: string; // subject behavior only
  };
  ensemble: {
    count: number | "all";
  };
  photoAction?: { // optional scene-specific override
    beats: Array<{
      mode: string;
      cue: string;
      holdChunks: number;
      prompt: string;
    }>;
    release: string;
    releaseHoldChunks: number;
  };
  sceneTransition?: {
    buttonLabel: string;
    portal: { summon: string; enter: string };
  };
  routes: MazeRoute[];
}
```

Place new images in `public/dataset/` and run `pnpm optimize:images`. Scene 1
uses `rose-garden/`, Scene 2 uses `cyberpunk-garden/`, Scene 3 uses
`asian-sculpture-garden/`, and Scene 4 uses `afro-futurism/`. Scenes 5–7 use the
stable `scenes/chapter-XX/scene-YY.webp` interface. Single-image metadata for the
first three replaceable Chapters contains only
`id / label / seedImage / seed / ensembleCount`; a shared factory supplies the
common Prompt. Source images may be 16:9 PNG files and should be converted to
WebP q90 before commit. A dynamic Server Component makes one variant selection
for each of the seven Chapters and passes those IDs to the client, preventing
hydration mismatch and avoiding a new seed selection during black-door
transitions. Even when Scenes 4 and 5 currently use the same image, each scene
draws independently.

Each `route` contains both audience-facing narrative and model-facing
`promptDelta.transition / settled` text. Selecting a variation uses the one-time
transition for the first forward chunk, then switches immediately after chunk
completion to a settled Prompt with no growth, appearance, or climbing process
verbs. Normal WASD, arrow-key, and mouse input sends only native SDK camera
input. The normal-exploration camera segment states both that the camera remains
still while idle and moves only while input is held, avoiding the race between
next-chunk `setPrompt()` latency and real-time input.
`composeWorldPromptSegments()` and `composePortalPromptSegments()` are the only
layered sources of truth; the string composer only joins segments with a single
space. The black door uses a compact layer version: Reactor uses three chunks to
finish a scene-native ornamental frame around an existing environmental arch or
doorway and stabilize uniform, featureless darkness beyond the threshold. It
then uses eight chunks whose `forward` action and portal Prompt agree while the
camera approaches, crosses the threshold, and fully enters darkness. The client
adds only a final push capped at 1.1×; the view inside the door and a fixed
curtain provide the actual blackout. The opening anchor remains a world-space
mark throughout. Route, photo, and portal actions are mutually exclusive. The
photo state machine uses a local monotonic chunk serial, so a `chunk_index` reset
inside a Reactor run cannot advance it prematurely.

Each of the seven black doors uses one destination-independent question, so a
random scene order cannot bind question copy to the wrong seed. All seven
questions, fourteen option labels, and fourteen choice IDs are globally unique.
Manually selecting the black door or reaching the 30-second limit enters the
same `pausing → choosing → preparing → resuming` state machine. Camera input is
released immediately and the scene timer freezes. The two answers become
available only after Reactor confirms pause. Once an answer is selected, the
black-door Prompt is preset while paused, so the first generated chunk after
resume enters the existing door flow directly. No environment Prompt is sent
during the question, the regular pause control remains locked, the dialog
explicitly states that billing continues while paused, and `End Session` remains
available. The seventh decision ends the authored journey and enters the
runtime-only Grand Palais finale flow.

`photoAction` is used only for special scene-specific overrides. When it is not
configured, `resolvePhotoAction()` uses only `ensemble.count` to distinguish
performer scenes from empty scenes. Performer counts never enter the shared
`LOOK HERE / HOLD / SHUTTER / release` Prompt.

The player is an invisible observer camera, not one of the people in the image.
All seed-visible performers retain their identity, position, and pose during
photos; none temporarily becomes the photographer.

Saved photos are raw Reactor main-video frames without HTML overlays, captured
after the simplified pose action is confirmed. The screen itself is the observer
camera. Photo mode uses the locked camera layer, and the Prompt never instructs
the model to “take a photo.”

## Prompt design principles

The project was refactored against Reactor's
[LingBot World 2 Prompt Guide](https://docs.reactor.inc/model-api-reference/lingbot-world-2/prompt-guide),
the official [`reactor-team/js-sdk` layered composer](https://github.com/reactor-team/js-sdk/blob/c67c276ec61f8d5221797dde36eea24b494b04fe/examples/lingbot-world-2/lib/lingbot-world-prompts.ts),
and the [LingBot World 2 extension skill](https://github.com/reactor-team/js-sdk/blob/c67c276ec61f8d5221797dde36eea24b494b04fe/examples/lingbot-world-2/skill/SKILL.md):

- All authored scenes share concise `base / anchor / movement / destination`
  segments. The seed image is the complete visual fact; the Prompt does not
  repeat performer counts, performer IDs, outfit lists, or per-person positions.
- The `anchor` asks only that seed-visible subjects and objects retain their
  current world position, depth, scale, pose, and support. A new pose target must
  first change the seed rather than accumulate corrective sentences.
- Camera, movement, destination, and event each own one axis. Large photo and
  portal events select compact layer versions to preserve budget for event
  detail.
- The portal event remains one present-progressive sentence describing the
  environment. Camera framing, chunk count, and threshold-crossing motion
  without lens zoom belong only to the camera layer, keeping text synchronized
  with the real `forward` state.
- Prompts describe positive visible facts by default. Only the camera contract
  and one specific ambiguity guard use necessary negative language.
- Actions must be brief, composable, and end in a stable state. A fresh session
  enables controls and photos only after confirming at least one complete
  ambient chunk whose `active_prompt` matches and whose
  `active_action === "still"`.
- Total Prompt length targets 1,000 characters with a 1,200-character hard cap:
  `base ≤ 220`, `anchor ≤ 220`, `camera ≤ 220`, `movement ≤ 180`,
  `destination ≤ 180`, each `event ≤ 300`, and `continuity ≤ 100`. Verification
  rejects model-facing performer counts and performer IDs such as
  `M01 / C01 / S01 / A01`. The Operator displays each segment's source and
  length.

## Reactor architecture

- `@reactor-team/js-sdk@2.12.1`
- `@reactor-models/lingbot-world-2@0.3.3`
- Model: `reactor/lingbot-world-2`
- Output track: `main_video`
- Token broker: `app/api/reactor/token/route.ts`
- React/session/controller: `components/FashionMazeExperience.tsx`

The project incorporates layered Prompt composition, layer versions, a pure
segment composer, next-chunk Prompt state, chunk-driven native camera pose,
base-SDK session clips, and operator telemetry from the official template. The
general example library, full layered editor, jump/crouch/orbit controls, and a
second token route were intentionally excluded to avoid maintaining two
applications.

`pause()` stops generation only; it does not release the GPU or stop billing.
Actually ending the experience requires `END SESSION` or the default
`disconnect()`.

### Deployment security boundary

The Grand Palais generation route does not validate browser Origin, Host, or
proxy headers. Localhost, IP, tunnel, preview, and production domains all use the
server-side OpenAI key directly to generate Scene 8. The key is always read only
on the server and never enters browser requests or responses. The route retains
the seven-reference allowlist, file boundaries, timeout, process-local
single-flight protection, and short cooldown.

The token broker and generation route currently have no login or distributed
rate limiting. If the application is deployed publicly, any caller may consume
Reactor or OpenAI quota. To control spend, add operator authentication,
distributed rate limits, and quotas at the hosting or reverse-proxy layer rather
than binding the application to an Origin. Root-level `reactor.key` and
`openai.key` files are mode `0600` and ignored by `*.key`, but they must still be
excluded explicitly when manually zipping or uploading the entire directory.
Production deployments should use only platform secrets named
`REACTOR_API_KEY` and `OPENAI_API_KEY`.

## Verification

```bash
pnpm typecheck
pnpm verify:prompts
pnpm verify:startup
pnpm verify:reconnect
pnpm verify:finale
pnpm verify:controls
pnpm verify:photo
pnpm verify:scene
pnpm verify:door
pnpm build
```

The eight `verify:*` commands do not connect to Reactor or OpenAI and consume no
credits. `prebuild` runs all verification automatically. The Prompt suite
exhaustively evaluates authored scene × entrance variant × route × photo beat ×
portal stage, checking randomized order, seven door questions, seed files, IDs,
anchors, layer ownership, photo-shutter semantics, and character budgets. The
current matrix covers seven authored scenes, 24 entrance variants, 240 authored
Prompt packets, and five runtime-finale packets. The longest combination is
933 / 1200 characters. Startup and reconnect suites cover disconnect edges, the
once-only gate, debug redaction, and reconnection decisions. Controls, photo,
scene, and door suites cover input arbitration, photo recovery, scene-transition
state, and door-question/reconnection gates. The finale suite covers seven
allowlisted references, ten waiting messages, the single-flight guard, and
runtime Scene 8 without making real API requests.

Do not select the live entrance in automated tests. Real connection testing must
be an explicit, credit-spending canary. Prompt or seed revisions must be
evaluated in a fresh session; continuing to hot-swap after bad frames have
entered autoregressive history does not prove a fix.

The static state machines for all seven authored-scene door decisions and Scene
8 generation have passed typechecking and the offline matrix. Actual door
distance, walking speed across eight confirmed `forward` chunks, browser push-in
feel, consecutive Reactor generations, and the timing of one OpenAI Images Edit
still require an explicit, credit-spending canary.

`submission/oneshot/` is a standalone delivery package and is not read by this
application. The local Scene 8 route reads the root-level `openai.key` as a
fallback for `OPENAI_API_KEY`.
